# CSP VillageMitra — Disaster Recovery & Backup Runbook

## 1. Overview & Recovery Objectives
This document establishes the official backup, recovery, and data preservation runbook for the CSP VillageMitra database and application infrastructure.

- **Recovery Point Objective (RPO)**: 24 Hours (Maximum allowable data loss window in disaster scenario).
- **Recovery Time Objective (RTO)**: 2 Hours (Maximum target time to restore a operational service instance).
- **Scope**: Modavalasa Gram Panchayat production datasets (16 core tables, 7 RPCs, row-level security policies, triggers, and survey microdata).

---

## 2. Supabase Infrastructure Backup Architecture
- **Platform Snapshots**: On the Supabase Free tier, daily physical backups are automatically generated by the underlying AWS WAL-G infrastructure and retained for 7 calendar days.
- **Limitation**: Self-service Point-in-Time Recovery (PITR) is restricted to the Supabase Pro tier. Therefore, application maintainers must execute scheduled logical exports to maintain independent recoverability.

---

## 3. Logical Backup Export Procedure

### Automated / CLI Export
Using the Supabase CLI with project connection credentials:
```bash
# 1. Export schema and data into a compressed custom-format dump
supabase db dump --project-ref mjpuyirbwaznnomzifyv --data-only -f backups/csp_villagemitra_data_$(date +%Y%m%d).sql

# Or using native PostgreSQL client tools (pg_dump)
pg_dump -h db.mjpuyirbwaznnomzifyv.supabase.co \
        -p 5432 \
        -U postgres \
        -d postgres \
        -Fc \
        -f backups/csp_villagemitra_backup_$(date +%Y%m%d).dump
```

## 4. Isolated Staging Restoration Drill Protocol

To verify that backups are actionable and uncorrupted, the following drill must be executed periodically into an isolated ephemeral local PostgreSQL instance or secondary staging database:

### Step 1: Initialize Ephemeral Database
```bash
# Create isolated test database
createdb -h localhost -p 5432 -U postgres csp_recovery_test
```

### Step 2: Apply Schema Migrations
```bash
# Apply baseline schema from repository migrations
for file in $(ls -1 supabase/migrations/*.sql | sort); do
    psql -h localhost -p 5432 -U postgres -d csp_recovery_test -f "$file"
done
```

### Step 3: Restore Data Payload
```bash
# Restore logical dump without overriding system privileges
pg_restore -h localhost \
           -p 5432 \
           -U postgres \
           -d csp_recovery_test \
           --data-only \
           --disable-triggers \
           backups/csp_villagemitra_backup_latest.dump
```

### Step 4: Verify Post-Restoration Invariants
Run the repository test suite against the restored database to prove object and constraint integrity:
```bash
node --test tests/*.test.js
```

Verification Checklist:
- [ ] All 16 core tables present and non-empty.
- [ ] Row-Level Security active on all tables.
- [ ] Triggers intact (`enforce_citizen_feedback_abuse_guards`, `trg_audit_logs_immutable`).
- [ ] Trigram search RPC (`search_portal`) operational with Telugu queries.
- [ ] Survey submission RPC (`submit_survey`) enforces atomicity and idempotency.
